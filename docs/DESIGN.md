# 사건 01 - 사라진 11분

## 콘셉트와 범위

한국어 디지털 조사 게임. 퇴직한 해양 관측 연구원 윤서진의 의뢰를 받아 23:14~23:25 관측 기록이 누락된 이유를 밝힌다. 초회 15~20분을 목표로 하지만 실제 소요 시간은 사용자 플레이테스트 전에는 확정하지 않는다. 외부 연결 없는 로컬 시뮬레이션. React UI와 순수 TypeScript 도메인 로직을 분리한다.

## 사건 흐름과 단서 연결도

1. 윤서진의 메일 → 의뢰 수락. 공개 사이트 `haeon.test`, 시민 기록 `tide.test`, 기록 검증 기관 `archive.test` 소개.
2. 해온 연구소 공지 → 이전 관측소 코드 MORA와 야간 감사 계정 `auditor` 발견.
3. 시민 조석 기록 → 교대 인계 규칙 '관측소 코드-사건 날짜(MMDD)'와 사건 날짜 10월 17일 → `MORA-1017` 추론.
4. `resolve haeon.test` → `10.17.0.11`; `scan` → 서버와 audit 서비스 확인; `connect ... auditor MORA-1017` → 감사 계정 연결.
5. `ls`, `read /audit/transfer.txt` → 외부 백업 `vault.archive.test`, 계정 `custodian`, 보관 키 `ECHO-2314` 발견. `collect /audit/revision.log` → 수정 이력 증거.
6. 기록원 웹에서 무결성 정책과 비교 방법 발견. `resolve vault.archive.test`, `scan`, `connect ... custodian ECHO-2314` → 백업 서버 연결.
7. 원본 관측 CSV와 승인 메시지 열람·수집. `compare` → 공개 데이터와 원본의 11분 차이, 지시자, 원인을 정리.
8. 메일로 조사 결과 제출: 범인·삭제 사유·시간대 선택과 3개 증거 필수. 잘못된 추론은 피드백 후 재시도, 증거는 유지.
9. 결말 분기: 독립 검증 기관 제출(검증 절차) 또는 시민 공개(즉시 공개). 두 선택 모두 같은 사실에 기반하며 서로 다른 결과를 보여준다.

## 데이터 구조

- World: 사이트 3개, 서버 2개, 도메인, 서비스, 사용자 권한, 가상 파일.
- GameState v1: 의뢰 상태, 방문 페이지/읽은 파일, 발견 도메인, 스캔 서버, 연결 세션, 수집 증거, 비교 결과, 힌트 단계, 제출 시도, 결말, 이벤트 기록, 터미널 기록, 메모.
- GameAction → reducer: 상태 전이와 이벤트. 순수 함수이며 네트워크/셸/DOM 접근 없음.
- CommandResult: 새 상태, 출력. 명령어 10개(help, resolve, scan, connect, ls, read, collect, compare, disconnect, clear).
- UI 별도: 창 위치/크기/순서/최소화, 브라우저 주소, 메일 선택, 입력 기록. 파일 보관함의 증거와 터미널은 동일 데이터 사용.
- localStorage: 버전 검증, 손상 저장 안내, 저장 실패 안내, 재시작 시 복구. 단일 플레이 세션을 지원.

## 성공·실패·힌트

성공은 3개 원본 증거 확보 + 대조 완료 + 올바른 사실 선택. 인증 실패, 미존재 파일, 권한 부족, 알 수 없는 명령은 복구 가능한 오류. 잘못된 제출은 재시도 가능. 시간 제한/영구 실패 없음. 현재 미완료 목표에 따라 3단계 힌트. 완료 조건은 명령 문자열이 아닌 세계 상태와 실제 파일 획득에서 판정.

## 화면 및 디자인

Hackspot 가상 데스크톱 + 6개 앱(터미널·브라우저·메일·폴더·메모장·액셀) + 진행 기록 플로팅 패널. 폴더는 수집한 증거·대조표를 보여주고 개인 메모는 별도 메모장 창에서 편집한다. 창 이동/크기/최소화/복원/최대화/포커스. 작은 화면은 창을 가용 영역에 맞춘다. 진행 기록은 모든 화면에서 기본적으로 숨기고 상단 오른쪽 점 세 개 버튼으로 연다. 바깥 클릭·포커스 이탈·닫기 버튼·Escape로 닫고 메모장 바로가기를 제공한다. 키보드: 터미널 ↑↓ 기록, Tab 자동완성, Ctrl+L 출력 지우기, Alt+1~6 앱, Escape 대화상자·패널 닫기. 한국어 IME 중 Enter 제출 금지.

콘셉트 생성 후 팔레트와 창 규격을 확정한다. 배경만 이미지이며 모든 텍스트, 버튼, 창, 아이콘은 코드 UI. 게임 장르상 캐릭터/스프라이트는 필요 없다.

## 완료 기준

- 순수 로직 테스트: 두 결말, 선행 조건, 권한, 중복 행동, 오류, 저장 왕복, 잘못된 제출.
- 브라우저에서 새 게임 → 사이트 읽기 → 명령어 조사 → 증거 확보 → 제출 → 결말을 직접 진행.
- 중간 reload 및 동일 진행 재개. 입력 기록/자동완성, 창 이동/크기/최소화/복원 확인.
- 타입 검사와 프로덕션 빌드 통과.
- 실제 검증 범위와 15~20분 목표를 구분해 README에 기록.

## 확정 디자인 토큰과 의도적 차이

- 콘셉트: docs/concept.png. 배경: public/ocean.png (이미지 생성 도구).
- 색: 바탕 #08131d, 창 #0d1923, 제목바 #14232e, 테두리 #3b5466, 본문 #dce7ee, 보조 #91a6b6, 강조 #65e3d5.
- 서체: 한국어 시스템 산세리프; 터미널 ui-monospace. 본문 14~15px/1.8, 제목 23~27px, 컨트롤 12~13px. 글자 확대 설정 제공.
- 창: 10px radius, 1px border, 어두운 shadow, 44px 제목바. 아이콘은 Lucide 1.7px outline.
- 레이아웃: 상단 43px, 하단 53px, 왼쪽 앱 레일 88px. 오른쪽 진행 패널은 너비 최대 320px, 모서리 20px, 반투명 배경·blur·그림자와 짧은 등장 효과를 사용한다. 고정 공간을 예약하지 않고 앱 창 위에 표시하며 낮은 화면에서는 내부 스크롤을 제공한다. 기본 메일 창 중앙 왼쪽, 터미널 창 오른쪽 아래.
- 콘셉트의 생성된 임의 메일 6개는 사건에 필요한 실제 의뢰/시스템 안내/후속 메일로 대체한다. 가짜 작성 버튼 대신 조사 결과 제출을 제공한다. 사건 날짜/내용은 위 확정 시나리오를 따른다. 헤더/버튼 추가는 저장, 새 게임, 글자 크기, 키보드 안내에 필요한 기능만 허용한다.
- 브라우저/증거/제출/결말 상태는 동일 창·색·타이포 체계를 확장한다. 소형 화면은 겹치는 창 대신 가용 영역에 맞춘 단일 포커스 창을 표시한다.

- 작업 표시줄 왼쪽은 검색 아이콘으로 앱·파일 검색 패널을 연다. 설치된 6개 앱, 수집한 증거, 완료한 대조표, 파일로 저장한 메모만 검색 대상으로 삼는다. 이름·경로·본문의 검색어를 모두 포함하는 결과를 표시하고 클릭 또는 ↑↓·Enter로 해당 앱·파일을 연다. 아직 수집하지 않은 자료는 노출하지 않는다. 진행 패널과 검색 패널은 함께 열리지 않는다.
- 작업 표시줄 오른쪽 진행 화살표를 제거하고 브라우저의 현재 로컬 시각을 자동 갱신해 표시한다. 메일 본문 등 사건 속 기록 시각은 시나리오 날짜를 따른다.

## 구현 정책 보완 (2026-10-31)

- 이미 단서를 아는 플레이어의 직접 접속을 허용한다. 공개 보고서와 세 증거를 실제로 확보·대조하면 공개 자료 조사 목표도 완료된다. 방문 이력을 허위로 추가하지 않는다.
- 최소화 후 복원은 앱 탐색 위치, 제출 초안, 미실행 입력을 보존한다. 2026-11-05 사용자 요청에 따라 X는 인스턴스를 해제하고 작업 표시줄에서 제거한다. 다시 실행할 때 초기 탐색·입력 상태로 연다. 터미널 연결·출력·명령 기록과 미저장 메모 초안은 종료 시 초기화하고, 수집 증거·저장 메모 파일·조사 진행은 유지한다. 새 게임은 파일과 앱 인스턴스까지 초기화한다. 새로고침은 GameState를 복구하고 UI 배치는 기본값으로 연다.
- 저장은 250ms debounce와 pagehide/beforeunload/visibilitychange flush를 사용한다. 이미 저장된 스냅샷을 종료 시 다시 쓰지 않는다. 저장 실패 시 재시도, 손상 저장은 사용자가 저장 재개를 선택할 때까지 원본 보존.
- 모바일에서 저장 안내가 조작을 막지 않도록 ‘나중에’로 접고 상태 표시에서 다시 연다. 자동 저장 중단 상태는 계속 표시한다.
- 명령은 512자 제한, 터미널 160개/명령 기록 100개/메모 10,000자 제한. 잘못된 help 인자도 문자열 안내로 처리한다. 참고 문서를 collect한 실패는 단서 열람으로 간주하지 않는다.
- 모달은 배경을 inert 처리하고 단축키 전환을 차단하며, 닫으면 호출 버튼에 포커스를 돌려준다. 조합 중 Enter 및 WebKit keyCode 229를 방어한다.

## 메모 파일과 앱 수명 (2026-11-05)

- 메모장 본문의 제목·설명·placeholder를 제거한다. 도구 모음의 새 메모·저장하기와 빈 편집 영역을 제공한다.
- 다른 이름으로 저장 화면은 저장 위치 사이드바, 경로 입력과 뒤로/상위 이동, 폴더·파일 목록, 새 폴더, 파일 이름·형식, 저장·취소를 제공한다. 같은 위치의 다른 파일을 저장하면 덮어쓰기를 확인한다.
- Finder 형태의 폴더 앱은 즐겨찾기, 뒤로·앞으로·상위, 경로, 아이콘/목록 보기, 현재 폴더 검색을 제공한다. 파일과 폴더 생성·이동·이름 변경 중 이름 충돌이나 자기 하위로의 폴더 이동은 거부한다. 폴더 이름이나 위치를 바꾸면 하위 경로를 함께 갱신한다.
- 더블클릭·열기·검색 결과로 텍스트와 로그는 메모장, EML은 메일, CSV는 액셀에서 연다. 증거 사본의 이름·폴더를 변경해도 원본 증거 ID와 본문은 유지된다. 액셀의 CSV 시트는 열/행 머리글, 셀 주소와 값, 방향키 이동을 제공한다.
- v1 저장에 선택적 noteFiles·folders·fileLocations를 추가한다. 기존 저장의 notes는 메모 초안으로 보존하고 폴더 누락은 기존 메모 경로와 기본 폴더에서 복구한다. 파일별 10,000자·최대 100개, 폴더 200개, 중복 식별자·경로·참조와 필드 값을 검증한다.
- 작업 중 초안과 저장 파일을 분리한다. 편집은 초안을 갱신하고 저장하기는 이름·경로가 있는 파일을 갱신한다. 새 메모나 다른 파일 열기로 미저장 수정이 사라질 때 확인한다.

# 사건 02 — 바뀐 교대표 (상세 기획안, 미구현)

### 콘셉트와 범위

- **장르:** 소규모 병원의 근무표 변경을 조사하는 초급 디지털 포렌식·절차 조사.
- **설계 난이도:** 1/10. 첫 플레이 10~15분을 목표로 하되, 실제 소요 시간은 플레이테스트 전까지 확정하지 않는다.
- **사건:** 새봄의료원은 2032-04-14 병동 교대표에 변경이 있었고 결재 기록이 없다는 내부 신고를 접수했다. 조사자는 병원 감사 담당자의 허가를 받아 비식별 읽기 전용 자료를 검토한다.
- **사건 유형·권한:** 침해 조사/내부 절차 검토. 의뢰 메일에는 승인번호 `SB-AUD-2032-0413`, 승인자 역할, 날짜 범위, 허용 자료(비식별 근무표·감사 로그·승인 대장), 허용 행위(읽기·수집·비교), 제외 대상(환자 자료·실제 계정·시스템 변경)이 명시된다.
- **핵심 결론:** 두 직원은 교대 변경에 서로 동의했고 최종 근무표에도 그 합의가 반영됐다. 다만 규정상 필요한 관리자 승인이 기록되지 않았다. 변경은 공유 계정 `ward-desk`로 저장되어 실제 조작자를 특정할 수 없으며, 악의적 변조나 외부 침입을 입증하는 증거는 없다.
- **학습 목표:** 기록의 사실성, 절차 위반, 개인의 의도, 계정 행위자를 서로 다른 판단으로 다룬다. “승인 기록이 없다”를 “승인이 절대 없었다” 또는 “특정 직원이 악의적으로 조작했다”로 확대하지 않는다.
- **범위 제외:** 환자 기록·진료 정보, 실제 의료기관이나 인물, 실서비스 접속, 비밀번호 추측, 취약점 악용, 네트워크 스캔, 실제 계정 로그인은 포함하지 않는다. 모든 자료와 도메인은 허구이며 `.test` 공간의 읽기 전용 시뮬레이션이다.

### 사건 흐름과 단서 연결도

#### 기본 타임라인

| 시각 (2032-04-13, 병원 현지 시각) | 기록                                                               | 조사 의미                                        |
| --------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------ |
| 17:40                             | 직원 A가 4월 14일 주간 근무와 직원 B의 늦은 근무를 맞바꾸자고 제안 | 변경 요청의 시작                                 |
| 18:03                             | 직원 B가 동의하고 직원 A가 재확인                                  | 교대 합의는 존재                                 |

| 18:42                             | 인계 메모에 “서로 합의함, 관리자 확인 대기” 기록                   | 현장 담당자가 승인 상태를 혼동했을 가능성        |

기존 근무표는 A가 07:00–15:00, B가 15:00–23:00이다. 최종 근무표는 두 근무가 서로 바뀌어 총 인원과 자격 구성이 유지된다. 직원 이름은 조사 화면에서 A/B로 마스킹하고 환자 데이터는 제공하지 않는다.

#### 플레이 순서

1. **의뢰 확인:** 메일에서 승인번호, 승인자 역할, 날짜·자료 범위, 허용 행위와 제외 대상을 확인한다. 조사 범위가 비어 있거나 모순되면 자료를 열지 않고 의뢰를 보류한다.
2. **작업공간 준비:** `ScopeGate`가 승인 메타데이터와 요청 작업의 일치 여부를 확인한다. 범위가 확인되면 사건 전용 작업공간을 만들고 필요한 가상 도구만 설치한다.
3. **정책 확인:** 병원 규정 페이지에서 교환 당사자 동의와 별도의 관리자 승인이 모두 필요하다는 점을 찾는다.
4. **근무표 비교:** 현재 근무표와 변경 전 스냅샷을 `RosterDiff`로 비교해 A/B 두 행의 시간이 서로 바뀌었음을 확인한다.
5. **합의 확인:** 메일 스레드에서 양측의 명시적 동의를 확인한다. 제안만 있었는지, 수락까지 있었는지 구분한다.
6. **자료 보존:** 읽기 전용 증거 사본을 `EvidenceVault`에 등록한다. 자료별 출처, 수집 시각, 사건 ID, 보존 상태를 기록하며 원본을 바꾸지 않는다.
7. **감사 기록 조사:** 수정 이력에서 변경 시각, 영향받은 두 행, 공유 계정, 결재 참조가 비어 있음을 확인한다. `LogTimeline`은 제공된 이벤트만 정렬한다.
8. **승인 대조:** 승인 대장에 해당 변경 신청이 없고 인계 메모에는 관리자 확인을 기다린다고 적혀 있음을 확인한다.
9. **타임라인 대조:** `compare`로 근무표·메시지·감사 로그·규정·승인 대장을 대조한다. 결과는 “합의된 변경이 승인 절차 전에 반영됨; 개인 조작자와 악의는 미확인”으로 요약한다.
10. **보고서 제출·정리:** 결론, 근거 파일, 확신 수준, 한계, 권고 조치를 선택한다. 내부 관리자 또는 독립 준법 담당자에게 제출한 뒤 가상 도구와 작업공간을 종료한다. 두 보고 경로 모두 개인정보 최소화 원칙을 지킨다.

각 페이지에는 자료 출처, 생성 시각, 현지 시간대, “읽기 전용 사본” 배지를 표시한다. 페이지 간 링크는 사건 메일과 조사 패널에서 제공한다. 로그인 화면이나 비밀 번호는 없으며 플레이어에게 승인된 조사 뷰어만 제공한다.

#### 가상 데스크톱 앱

- **필수:** 브라우저(사이트 열람), 메일(의뢰·교대 합의), 폴더(증거 수집), 액셀(CSV 비교), 메모장(개인 조사 메모·보고서 초안), **도구 보관함(Toolbox)**(가상 조사 프로그램 설치·권한 확인).
- **선택:** 터미널은 수집한 텍스트 자료의 로컬 열람·검색에만 쓸 수 있다. 네트워크 접속이나 권한 상승은 이 사건의 목표가 아니다.
- **이 사건에 설치할 가상 도구:** `RosterDiff`(근무표 버전 비교), `LogTimeline`(제공된 감사 이벤트 정렬), `EvidenceVault`(출처·수집 이력 보존), `ReportKit`(근거·한계·권고를 분리한 보고서). `ScopeGate`는 기본 제공한다. 침투·취약점 공격 도구는 이 사건과 무관하므로 카탈로그에 설치 후보로 표시하지 않는다.
- **실제 포렌식 도구와의 구분:** 사건 02에는 패킷 캡처나 디스크 이미지가 없으므로 Wireshark·Autopsy를 사용하지 않는다. 이 사건에 맞는 근무표·감사 기록 프로그램만 선택하는 것이 현실적인 도구 선택이다. 별도 사건에서 합성 샘플을 제공하는 경우에만 실제 Wireshark/Autopsy 오프라인 분석 안내를 선택형으로 연결한다.
- **가상 설치 동작:** 도구 카탈로그에서 가상 게시자, 버전, 로컬 출처, 무결성 상태, 허용 자료와 권한을 확인하고 **설치**를 누르면 사건 작업공간에 가상 앱이 추가된다. 설치·실행·제거 이력은 사건 로그에 남는다. 실제 바이너리 다운로드·실행, OS 권한 상승, 임의 호스트 입력은 없다. 모든 도구는 승인서가 허용한 자료 사본만 처리한다.
- **설치:** 새로운 실제 프로그램이나 npm 의존성을 추가하지 않는다. 현행 데스크톱은 6개 앱이며, 사건 02 도입 시 Toolbox를 일곱 번째 가상 앱으로 추가한다. 구현 시 개발 환경은 저장소의 현재 요구 버전(Node.js 22.13 이상)과 `npm ci`를 사용한다.

### 데이터 구조 제안

콘텐츠는 `world.ts`의 정적 가상 사이트·문서 데이터로 두고, 사건 진행은 순수 리듀서 상태로 관리한다. 실제 사람·환자 정보, 외부 API, 백엔드 저장소는 만들지 않는다.

```ts
type Case02EvidenceId =
  | 'roster-before'
  | 'roster-after'
  | 'swap-thread'
  | 'revision-log'
  | 'shift-policy'
  | 'approval-register'
  | 'handover-note';

type Case02ToolId = 'scope-gate' | 'roster-diff' | 'log-timeline' | 'evidence-vault' | 'report-kit';

interface EvidenceManifestEntry {
  evidenceId: Case02EvidenceId;
  source: string;
  collectedAt: string;
  access: 'read-only-copy';
  integrityStatus: 'verified' | 'not-verified';
}

interface ShiftAssignment {
  date: string;
  ward: 'B';
  staffAlias: 'A' | 'B';
  shiftStart: string;
  shiftEnd: string;
  role: string;
}

interface RevisionEvent {
  id: string;
  occurredAt: string;
  actorAccount: 'ward-desk';
  changedAliases: Array<'A' | 'B'>;
  approvalId: string | null;
}

interface Case02State {
  accepted: boolean;
  scopeVerified: boolean;
  installedToolIds: Case02ToolId[];
  visitedPages: string[];
  readFiles: Case02EvidenceId[];
  collectedEvidence: Case02EvidenceId[];
  evidenceManifest: EvidenceManifestEntry[];
  compared: boolean;
  findings: {
    assignmentsExchanged: boolean | null;
    bothStaffAgreed: boolean | null;
    approvalRecorded: boolean | null;
    individualActorKnown: boolean | null;
    maliciousIntentSupported: boolean | null;
  };
  hintLevel: number;
  attempts: number;
  ending: 'management' | 'compliance' | null;
}
```

- `ScopeGate`가 승인번호·승인자 역할·기간·허용 자료·금지 행위를 대조한다. 실패하면 새 자료 열기와 가상 도구 설치를 차단하고 범위 수정 요청만 가능하다.
- 도구 카탈로그는 로컬에 정의된 가상 프로그램 메타데이터만 표시한다. `toolId`, 표시 이름, 버전, 허용 입력, 권한, 허용 사건 유형을 검증하며 코드나 외부 설치물을 받지 않는다.
- `EvidenceManifestEntry`는 증거가 어디서 언제 어떤 접근 모드로 확보됐는지 남긴다. 무결성 상태는 시뮬레이션 메타데이터이며 이를 실제 병원 기록의 진위를 증명하는 값으로 표현하지 않는다.
- `ShiftAssignment`는 변경 전·후 두 스냅샷을 표현한다. 날짜·시각은 병원 현지 시간대로 고정해 시간대 환산 퍼즐을 만들지 않는다.
- `RevisionEvent.actorAccount`는 공유 계정만 기록한다. 직원 개인 ID나 실명으로 변환하는 숨은 정답은 두지 않는다.
- `approvalId: null`은 해당 이벤트에 결재 참조가 남지 않았다는 뜻이다. 이를 승인 행위가 절대 없었다는 증명으로 취급하지 않는다.
- 증거는 읽기와 수집을 구분하고 기존 파일 보관함·액셀·메일 열기 흐름을 재사용한다. `compare` 결과는 증거가 아니라 파생된 분석표로 저장한다.
- 잘못된 제출은 `attempts`만 늘린다. 수집한 증거와 정답에 필요한 조사 상태는 유지한다.
- 저장 데이터에 `case-02`를 추가할 때 기존 v1 저장과 호환되도록 선택 필드로 도입하고, 잘못된 상태를 자동으로 성공 처리하지 않는다.

### 성공·실패·힌트

#### 성공 판정

핵심 증거 다섯 종류(변경 전·후 근무표, 양측 합의 메일, 감사 로그, 근무 변경 규정, 승인 대장)를 확보하고 비교한 뒤 아래 내용을 제출해야 한다.

1. 두 근무 행이 바뀌었고 두 직원이 변경에 동의했다.
2. 규정상 관리자의 사전 승인이 필요하지만 조사 자료에서 승인 기록을 찾지 못했다.
3. 수정 계정은 공유 계정이므로 실제 작업자를 특정할 수 없다.
4. 현재 증거만으로 악의적 변조, 계정 침해, 환자 피해를 주장할 수 없다.
5. 공유 계정 폐지, 개인별 계정·감사 추적, 승인 완료 후에만 근무표를 확정하는 통제를 권고한다.
6. 분석 전에 조사 범위를 확인했고, 설치한 가상 도구는 승인된 비식별 자료만 처리했다.

#### 실패와 복구

- **행위자 단정:** `ward-desk` 계정을 특정 직원과 동일시하면 감사 로그의 한계를 설명하고 재검토를 요청한다.
- **악의 단정:** 승인 누락만으로 고의 은폐나 침입이라고 결론 내리면 합의 메일·인계 메모·승인 대장을 다시 확인하게 한다.
- **합의와 승인 혼동:** 직원들의 합의가 관리자 승인을 대체한다고 답하면 정책 페이지를 안내한다.
- **과도한 부정:** 근무표 변경 자체를 조작으로 단정하면 변경 전·후 버전과 양측 메시지를 대조하게 한다.
- **민감 정보 노출:** 직원 실명이나 불필요한 정보를 공개 보고서에 넣으면 비식별 보고서로 수정하도록 한다. 환자 자료는 애초에 제공하지 않는다.
- 오답은 영구 실패나 시간 제한을 만들지 않는다. 재시도해도 기존 증거는 보존한다. 완료 경로는 사실 판단과 보고 경로 선택을 분리한다.
- 범위 밖 자료나 도구를 요청하면 시뮬레이터가 동작을 거부하고 감사 이벤트를 남긴다. 올바른 선택은 작업을 멈추고 권한을 재확인하는 것이다.

#### 3단계 힌트

1. **관찰:** 변경 전·후 근무표에서 실제로 바뀐 행과 변경 시각을 먼저 찾는다.
2. **연결:** 직원 간 동의는 메일에서, 관리 승인 여부는 규정과 승인 대장에서 확인한다.
3. **결론:** 공유 계정은 사람을 특정하지 못한다. “합의된 변경이 승인 전에 반영됨”은 뒷받침되지만 침입이나 악의는 입증되지 않았다.

### 화면 구성과 디자인

- 데스크톱, 창, 작업 표시줄, 창 동작, 앱 전환은 기존 Hackspot 디자인을 그대로 쓴다. 병원 사건을 위한 별도 데스크톱은 만들지 않는다.
- Toolbox는 기존 앱과 같은 창 스타일을 쓰는 가상 카탈로그 화면이다. 각 도구 카드에는 게시자, 버전, 출처·무결성 상태, 기능, 허용 자료, 권한, 오프라인/시뮬레이션 표시를 제공한다. 설치 흐름은 세부 확인→범위 검사→무결성 확인→설치→사건 로그 기록이며, 승인 범위 밖 도구는 비활성화하고 이유를 텍스트로 설명한다.
- 병원 페이지는 기존 브라우저 창 안에서 차분한 백색·옅은 청색의 업무 포털로 표시한다. 기준색은 기존 어두운 데스크톱과 충돌하지 않게 페이지 내부에 한정한다: 배경 `#f5f8fa`, 제목 `#17324d`, 링크·선택 `#287b83`, 주의 `#9a681e`.
- 근무표는 날짜·병동·역할·시간 열을 가진 의미 있는 표로 만든다. 변경 행에는 “변경됨” 표식과 이전 값 보기 기능을 제공하고 색만으로 상태를 구분하지 않는다.
- 감사 페이지는 시간, 계정, 작업, 영향받은 별칭, 승인 참조 열을 표시한다. 계정이 공유 계정임을 텍스트로 분명히 밝힌다.
- 정책 페이지는 “직원 간 합의”와 “관리자 승인”을 별도 단계로 시각화한다. 승인 대장에 항목이 없을 때는 “검색된 기록 없음”이라고 표시하고, 시스템 전체에 기록이 없다고 과장하지 않는다.
- 사건 메일에는 범위와 개인정보 최소화 안내를 먼저 보여준다. 완료 화면은 사실, 미확인 사항, 권고를 구분한다.
- 기존 글자 확대·키보드 탐색·모바일 단일 창을 지원한다. 작은 화면에서는 표에 가로 스크롤을 제공하고 핵심 열을 읽을 수 있게 한다.

### 완료 기준

- **콘텐츠:** 시나리오 전체에서 날짜·근무 시간·계정·승인 규정이 일관되며, 환자 정보와 실제 조직 정보가 포함되지 않는다.
- **증거 흐름:** 각 자료를 열람·수집한 뒤 출처와 파일명이 보관함에 표시되고, 필수 증거가 모이기 전에는 비교·제출이 완료되지 않는다.
- **권한·도구:** 정상 승인서에서는 해당 가상 도구만 설치되며, 승인 누락·범위 초과 요청은 차단된다. Toolbox 동작이 실제 네트워크·명령 실행·외부 다운로드를 하지 않는지 검사한다.
- **추론 테스트:** 변경 사실, 직원 합의, 승인 기록 누락은 올바르게 판별할 수 있다. 공유 계정만으로 개인을 지목하거나 침입·악의를 자동 추론하는 답은 거부한다.
- **오류 회귀:** 증거 일부 누락, 중복 수집, 페이지 직접 방문, 잘못된 보고서, 힌트 1→2→3, 재시도 후 증거 보존을 검증한다.
- **브라우저 E2E:** 메일 수락 → 정책/근무표/감사 기록 열람 → 증거 수집 → 비교 → 두 보고 경로 중 하나로 제출 → 결말 확인을 끝까지 수행한다.
- **저장·접근성:** 중간 새로고침 후 진행이 복구되고, 키보드만으로 표·증거·제출을 사용할 수 있으며, 데스크톱과 모바일에서 텍스트가 잘리지 않는다.
- **기술 검증:** 순수 로직 테스트, 기존 검사 명령, 프로덕션 빌드를 통과한다. 테스트 중 실제 네트워크 요청이나 외부 프로그램 실행이 없어야 한다.
- **범위 기록:** 초회 10~15분은 목표치일 뿐이며, 실제 사용자 플레이테스트 후 README에 측정된 결과와 검증 범위를 기록한다.
