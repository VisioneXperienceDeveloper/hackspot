# 백엔드 개발 작업 매뉴얼

작성일: 2026-11-03  
대상: 사용자와 백엔드 작업을 수행하는 AI 에이전트  
출처: 사용자가 제공한 「백엔드 개발자 메뉴얼」. 중복을 통합하고 오타를 수정했으며, 적용 조건과 검증 기준을 보완했다. 특정 제품의 최신 명령·요금·기능을 검증한 문서는 아니다.

## 1. AI가 이 문서를 사용하는 방법

- 백엔드 작업을 시작할 때 저장소의 `AGENTS.md`, 실행 스크립트, 의존성, 기존 구현과 문서를 먼저 확인한다.
- 사용자 요청과 저장소 지침을 우선하며, 이 문서는 기본 작업 기준으로 사용한다.
- 요청과 관련된 절만 적용한다. 작은 변경에 전체 인프라나 추상화를 추가하지 않는다.
- 기존 스택과 패턴을 우선한다. NestJS, Spring, Kotlin, Prisma 등은 선택 가능한 예시이며 필수 기술이 아니다.
- **기본**은 해당 작업에서 우선 적용할 원칙, **조건부**는 필요와 환경을 확인해 적용할 항목, **초기값**은 측정·팀 합의로 조정할 값이다.
- 구현 후 관련 검증을 실행하고, 실행한 검증과 미검증 사항을 구분해 보고한다. 설정 파일 작성만으로 실제 보호·백업·배포가 작동한다고 보고하지 않는다.
- 파괴적 초기화, 운영 데이터 변경, 배포, 외부 알림 전송은 사용자의 승인 범위를 확인한다. 문서의 예시를 실제 실행 지시로 해석하지 않는다.

### 작업 순서

1. 요청 범위와 현재 상태를 확인한다.
2. 관련 절에서 필요한 기준만 선택한다.
3. 코드·설정·문서를 함께 변경한다.
4. 변경 위험에 맞는 테스트와 실행 검증을 수행한다.
5. 변경 내용, 검증 결과, 남은 제약을 보고한다.

## 2. 환경 설정과 프로젝트 시작

### 재현 가능한 개발 환경

- 기본: DB·캐시·메시지 큐 등 외부 의존성을 Docker Compose 또는 프로젝트의 동등한 환경으로 제공한다.
- Compose 설정은 프로젝트 루트에 두고, 데이터 영속성을 위한 볼륨과 서비스 준비 상태 확인을 구성한다.
- 로컬 포트·비밀번호는 `.env`, 변수 설명과 빈 예시는 `.env.example`로 관리한다. 비밀값은 커밋하지 않는다.
- README에는 사전 조건, 환경 파일 준비, 의존성 설치, 마이그레이션, 실행, 확인 방법을 포함한다. 단일 실행 명령만으로 필요한 준비 과정을 생략하지 않는다.
- 예시 실행 명령은 `docker compose up -d`. 기존 환경이 레거시 `docker-compose`를 사용한다면 실제 지원 버전을 확인한다.
- `docker compose down -v`는 볼륨 데이터를 삭제한다. 초기화가 필요한 로컬 환경에서 대상과 백업을 확인한 뒤 사용한다.

### 보일러플레이트와 개발 도구

- 템플릿에는 인증·인가, 에러 처리, 로깅의 최소 구조를 준비한다.
- `.gitignore`, `.editorconfig`, 포매터·린터 설정, `.env.example`을 포함한다.
- 스택별 템플릿을 분리하고 의존성과 실행 절차를 주기적으로 점검한다. GitHub 템플릿 저장소를 활용할 수 있다.
- 자주 쓰는 패턴 5개부터 IDE 스니펫으로 등록한다. 세 번 이상 반복 복사한 코드는 후보로 삼는다.
- 공유 가능한 `.vscode` 설정·스니펫·`launch.json`은 저장소에 포함하되 개인 경로나 비밀값은 제외한다.

### Git과 의존성

- 기본 브랜치 모델: `main` 통합, `feature/*` 기능, `release` 배포, `fix/*` 수정. 기존 저장소의 배포 모델이 있으면 따른다.
- `main`·`release`에 PR과 필수 CI 검사를 요구한다. 실제 차단에는 호스팅 서비스의 브랜치 보호·ruleset 설정이 필요하다.
- 완료·병합된 작업 브랜치를 정리하고 브랜치 전략을 README 또는 CONTRIBUTING에 기록한다.
- 선택한 패키지 관리자의 lockfile을 커밋하고 재현 가능한 설치 명령을 사용한다. npm 프로젝트의 예시는 `npm ci`다.
- Dependabot 또는 Renovate로 업데이트를 확인한다. 원문 기준으로 자동 병합은 사용하지 않는다.

### 로컬 DB 백업

- 조건부: 보존할 로컬 데이터가 있다면 `scripts/`의 백업 스크립트를 스케줄러로 실행한다.
- DB에 맞는 도구를 사용한다. MySQL은 `mysqldump`, PostgreSQL은 `pg_dump`다.
- 초기값: 일일 백업, 최근 7일 보관, 월 1회 실제 복원 확인.
- 날짜가 포함된 파일명을 사용한다. 백업 파일은 Git이 아닌 접근이 제한된 저장소에서 보관한다.
- 실행 중인 DB 볼륨을 단순 압축하는 방식은 일관성을 보장하지 않을 수 있다. DB가 지원하는 덤프·스냅샷 절차를 사용한다.

## 3. 설계

### 데이터와 API 계약

- 핵심 엔터티 약 5개부터 간단한 ERD를 작성하고 실제 도메인 관계를 표현한다. 필요한 M:N 관계를 억지로 1:N으로 바꾸지 않는다.
- 필수 컬럼과 제약조건부터 정하고, 미확정 항목은 TODO로 남긴다. ERD 원본을 버전 관리한다.
- OpenAPI/Swagger 등 코드와 동기화할 수 있는 API 명세를 사용한다.
- 인증 방식, 요청·응답 DTO, 타입, 필수 필드, 예시, 상태 코드, 오류 형식을 명시한다.
- 개발 환경의 `/api-docs` 등 안정된 경로를 제공하고, 문서 생성·검증을 CI에 포함한다. 공개 범위는 환경에 맞게 정한다.

### 구조와 공통 기능

- 기본 구조는 컨트롤러 → 서비스/유스케이스 → 데이터 접근 계층이다. 이미 ORM이 충분한 경계를 제공하면 중복 래퍼를 의무화하지 않는다.
- 인증·인가, 전역 오류 처리, 로거 설정을 먼저 일관되게 구성한다.
- 응답 형식을 통일한다. `{ success, data, error }`는 예시이며 기존 API 계약과 HTTP 상태 코드 의미를 유지한다.
- 공통 날짜 처리·페이지네이션 등은 역할이 명확한 공유 모듈에 둔다. 도메인 로직을 무조건 `shared`에 모으지 않는다.
- DI를 활용하고, DB 연결·설정처럼 수명주기가 분명한 객체에 공유 인스턴스를 사용한다.
- 결제·알림·파일 저장 같은 외부 연동은 클라이언트/어댑터로 경계를 만든다.
- 전략 패턴 등은 실제 교체 요구가 있을 때 적용한다. 예상만으로 인터페이스와 계층을 늘리지 않는다.

### 테스트와 마이그레이션 계획

- 금전 처리, 권한, 핵심 흐름, 반복 결함에 우선순위를 둔다.
- 서비스 로직은 단위 테스트, 요청·인증·DB 연결은 통합 테스트, 중요한 전체 흐름은 E2E로 확인한다.
- 단위 테스트를 많이 두는 구성을 출발점으로 삼되 개수 비율을 목표로 삼지 않는다.
- 커버리지 70~80%는 원문의 참고 목표다. 수치보다 중요한 분기와 실패 경로 검증을 우선한다.
- 스키마 변경은 순서가 명확한 마이그레이션 파일로 관리하고 Git에 포함한다. 운영 DB의 수동 변경을 기본 절차로 사용하지 않는다.
- 스테이징에서 적용·복구를 검증한다. 되돌릴 수 있는 변경은 역마이그레이션을, 데이터 손실 가능성이 있는 변경은 백업 복구 또는 전진 수정 절차를 준비한다.
- 앱 이전 버전과의 스키마 호환성을 검토한다. 애플리케이션 롤백이 DB 복구를 자동으로 해결하지는 않는다.

## 4. 구현

### API와 비즈니스 로직

- 단순 CRUD는 제너레이터를 활용하고 생성된 권한·검증·노출 필드를 검토한다. 복잡한 로직은 명시적으로 구현한다.
- 컨트롤러는 요청 파싱·검증·응답 변환에 집중하고 비즈니스 규칙은 서비스에 둔다.
- 함수는 책임과 동작이 드러나도록 작게 나눈다. 서비스 간 의존성은 도메인 책임을 기준으로 정리한다.
- DB 접근과 비즈니스 규칙의 경계를 유지하고, 필요한 필드만 DTO/직렬화 계층으로 반환한다.

### 트랜잭션과 외부 API

- 여러 데이터 변경이 하나의 원자적 작업이면 서비스/유스케이스에서 트랜잭션을 명시한다.
- 범위와 시간을 최소화하고 실패·롤백 시나리오를 테스트한다.
- 외부 API 호출은 DB 트랜잭션 밖에 둔다. 양쪽 상태의 일관성이 필요하면 멱등성, 보상 처리, outbox 등 적절한 방법을 선택한다.
- 외부 서비스마다 전용 클라이언트를 두고 응답을 내부 모델로 변환한다.
- 타임아웃과 재시도 한도를 정한다. 재시도는 일시적 실패와 안전하게 반복 가능한 요청에 적용한다.
- 테스트에서는 대체 클라이언트나 Mock을 사용하고, 비밀값은 환경 설정 경계에서 주입한다.

### 배치·큐·캐시

- 배치는 스케줄러에 등록하고 시간대, 크론 표현식의 의미, 시작·종료·실패 결과를 기록한다.
- 중복 실행과 중복 처리를 방지하고 긴 작업은 청크로 나눈다. 다중 인스턴스에서는 프로세스 내부 플래그만으로 중복 실행을 막지 않는다.
- 실패 알림은 기존 채널과 운영 정책에 맞춰 구성한다.
- 이메일·알림·리포트처럼 오래 걸리는 작업은 필요 시 큐/워커로 분리한다. BullMQ와 Bull Board는 선택지다.
- 비동기 API는 접수 결과와 작업 ID를 제공하고, 필요하면 상태 조회 API와 진행 UI를 연결한다. 실패 재시도 후 최종 실패 처리도 정한다.
- 캐시에는 TTL, 키 규칙, 데이터 변경 시 무효화, 장애 시 동작을 정의하고 적중률을 측정한다.
- 세션 캐시는 단순 조회 캐시와 달리 보안·로그인 상태에 영향을 주므로 장애 시 허용 범위를 별도로 정한다.

## 5. 테스트와 디버깅

- 변경에 맞는 최소한의 신뢰할 수 있는 테스트를 실행한다. 결함 수정에는 재현 가능한 회귀 검증을 추가한다.
- Postman 컬렉션과 Newman은 API 회귀 테스트의 선택지다. 기존 통합 테스트가 같은 계약을 충분히 검증한다면 중복 도구를 강제하지 않는다.
- 테스트 환경의 base URL·토큰을 분리하고 비밀값을 컬렉션에 넣지 않는다.
- 로그는 `debug`, `info`, `warn`, `error`로 구분한다. 운영은 보통 `info` 이상, 상세 과정은 `debug`, 예외는 적절한 스택과 함께 기록한다.
- JSON 구조와 요청/추적 ID를 통일한다. 요청 메타데이터 위주로 기록하고 비밀번호·토큰·민감 본문을 제외한다.
- Sentry 등 오류 추적은 환경을 분리한다. 사용자 ID·IP는 필요성과 개인정보 처리 정책을 확인하고 최소 수집·마스킹한다.
- 해결된 오류를 정리하고 반복 오류가 실제로 재발하지 않는지 확인한다.
- 부하 테스트는 핵심 API 3~5개부터 시작해 p95/p99, 오류율, 처리량, 자원 사용량을 함께 본다. 운영 결제나 실사용자 데이터가 영향을 받는 시험은 승인된 환경에서 수행한다.
- 디버깅 시 조건부 브레이크포인트, Watch, Call Stack, 비동기 스택을 활용한다.

## 6. 배포와 인프라

### CI/CD와 이미지

- PR에서 설치 → 린트/타입 검사 → 테스트 → 빌드를 검증하고 필수 검사 실패 시 병합을 차단한다.
- 배포 트리거는 실제 운영 브랜치를 따른다. 원문의 기본 예시는 `release`다.
- CI 비밀값은 GitHub Secrets 등 제공되는 비밀 저장소에 보관한다.
- Docker는 멀티 스테이지 빌드와 `.dockerignore`를 사용하고 의존성 파일을 먼저 복사해 설치 캐시를 활용한다.
- 런타임에는 필요한 의존성과 산출물만 포함한다. npm의 예시는 `npm ci --omit=dev`이며 빌드 단계 의존성은 별도로 확보한다.
- Alpine은 선택지다. 네이티브 모듈·libc 호환성을 확인하고 필요하면 다른 경량 이미지를 사용한다.
- 이미지 크기와 실행 가능성을 검증하고 커밋 해시 또는 버전으로 배포 산출물을 식별한다.

### 환경 설정과 롤백

- `.env`는 로컬 개발에 사용하고 운영 비밀값은 플랫폼의 비밀 관리 기능을 사용한다.
- Kubernetes에서는 민감 설정과 일반 설정을 Secret·ConfigMap 등으로 구분한다. Secret 리소스 사용만으로 모든 저장·접근 보안이 해결되지는 않는다.
- 환경변수는 용도별로 정리하고 시작 시 필수 설정을 검증한다.
- 설정 변경에 재시작·재배포가 필요한지 문서화한다. 무배포 적용은 동적 설정이 실제로 필요한 경우에만 설계한다.
- 초기값: 이전 이미지 최소 5개 보관. 보존 수는 저장 비용과 복구 요구에 맞게 조정한다.
- 롤백 명령, 대상 버전 선택법, DB 호환성, 복구 후 확인 방법을 런북에 기록하고 스테이징에서 시험한다.

### 헬스체크와 배포 중 요청 보호

- `/health` 등 상태 확인 경로를 제공한다. 필요하면 liveness와 readiness를 분리한다.
- liveness는 프로세스의 진행 가능성, readiness는 트래픽 수신 가능성을 확인한다. 외부 DB 장애를 liveness에 무조건 연결해 재시작을 반복하지 않는다.
- 초기값: 상태 검사 간격 10~30초. 실패 임계값·타임아웃은 서비스에 맞게 조정한다.
- 종료 시 신규 요청을 중단하고 진행 요청·작업·연결을 정리하는 graceful shutdown을 구현한다.
- 무중단 배포가 필요하면 다중 인스턴스, 로드밸런서, 준비 상태 검사, 롤링 배포와 종료 유예를 함께 검증한다. graceful shutdown만으로 무중단을 보장하지 않는다.
- Kubernetes의 `preStop`, `terminationGracePeriodSeconds`, 레플리카 2개 이상은 해당 배포 방식의 구성 예시다.

## 7. 모니터링과 운영

- 필요에 따라 APM/분산 추적을 연동한다. New Relic, Datadog, Elastic APM, Jaeger, SigNoz는 후보이며 요금·지원 범위는 선택 시 확인한다.
- 로그는 기존 플랫폼에 중앙화한다. ELK, CloudWatch, Loki/Grafana 등을 선택할 수 있다.
- 로그 보존 30일은 초기값이다. 비용, 보안, 개인정보 처리와 진단 요구에 맞춘다.
- 알림은 대응이 가능한 조건으로 만든다. 사용자 영향이 있는 긴급 장애는 Critical, 추세 확인은 Warning으로 구분한다.
- 지속 시간, 담당자, 대시보드, 대응 런북, 에스컬레이션 기준을 알림에 연결하고 월 1회 이력을 검토한다.
- 슬로우 쿼리는 MySQL의 `slow_query_log`, PostgreSQL의 `log_min_duration_statement` 또는 관리형 DB 기능으로 수집한다. 1초는 초기 후보 값이다.
- 주간 슬로우 쿼리 Top 10과 ORM 생성 쿼리를 검토하고 실행 계획으로 원인을 확인한다.
- 운영 백업은 복구 목표 시간(RTO)과 허용 데이터 손실 시간(RPO)을 기준으로 정한다. 일일 백업·7일 이상 보관은 출발점이며 목표에 따라 PITR 등을 검토한다.
- 백업은 접근을 제한하고 별도 스토리지나 리전에 보관한다. 분기별 실제 복원 훈련으로 데이터와 앱 동작, 복구 시간을 확인한다.
- 디스크·메모리·CPU·프로세스·DB 연결·Redis 메모리 점검을 스크립트화한다. 플랫폼 모니터링과 중복되지 않게 구성한다.
- 점검 스크립트를 버전 관리하고 필요한 주간 리포트를 작성한다. 외부 알림 발송은 승인된 수신처와 정책을 따른다.

## 8. 성능 개선과 리팩터링

- 추측보다 측정을 우선한다. 병목 요청, 실제 SQL, 실행 계획, 자원 지표를 확보한다.
- N+1은 적절한 배치 조회·JOIN·eager loading으로 해결하되 결과 행 수와 데이터량을 함께 확인한다.
- 복잡한 조회는 필요 시 매개변수 바인딩된 SQL을 사용한다.
- `WHERE`, `JOIN`, `ORDER BY`를 기준으로 인덱스를 검토한다. 복합 인덱스 순서는 단순 카디널리티 규칙이 아닌 실제 조건·정렬·범위와 실행 계획으로 결정한다.
- 인덱스의 읽기 효과와 쓰기 비용을 확인하고 미사용 여부는 충분한 관찰 기간 후 판단한다.
- 목록/상세 DTO를 구분하고 페이지네이션·최대 조회량을 정한다. 큰 본문은 필요한 응답에만 포함하고 압축은 플랫폼 지원과 함께 검토한다.
- 커넥션 풀은 기본값에서 측정으로 조정한다. 10~50은 원문의 예시이며 전체 인스턴스 수와 DB 연결 한도를 함께 계산한다.
- 유휴 연결과 획득 타임아웃을 정하고 풀 대기·사용량을 관찰한다.
- 리팩터링은 요청 범위 안에서 한 가지 목적씩 수행한다. 동작 검증을 확보하고 기능 변경과 분리 가능한 커밋·PR로 정리한다.
- 큰 구조 변경은 별도 작업 브랜치에서 검증하고 변경 이유·범위를 PR에 기록한다.
